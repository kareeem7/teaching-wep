# تصميم المصادقة والاستعادة — AUTH_DESIGN

**الحالة:** تصميم للمرحلة ٠٢ · **الأساس:** C-06، C-07، C-08، C-09، C-24، C-25 · **آخر تحديث:** 2026-11-04
**تحذير:** هذا تصميم على ورق. **لم يُختبر أي شيء منه**، وبعض التفاصيل تعتمد على سلوك Supabase Auth الفعلي ويجب التحقق منها عمليًا في أول يوم من المرحلة ٠٢ (قائمة تحقق في §٧).

## ١) المطلوب تثبيته

1. طالب يدخل **بهاتف + كلمة مرور فقط** (C-28)، **بلا SMS مدفوع وبلا بريد**.
2. مدرس يُدعى فقط، ويضبط كلمة مروره عند التفعيل؛ لا تسجيل عام.
3. كلمة المرور لا تُقرأ من أي دور إداري؛ الاستعادة تُصدر رابطًا لا كلمة مرور.
4. تغيير كلمة المرور أو إيقاف الحساب يُبطل الوصول وفق سياسة معتمدة.
5. كل حدث أمني يُسجَّل في `app.audit_log`.

## ٢) قرار هوية الدخول — **مغلق بقرار العميل (C-28)**

### القرار
**هوية الدخول = رقم هاتف + كلمة مرور، فقط.** أُلغي «كود الطالب + كلمة مرور» كنوع دخول.

**مصدر القرار:** العميل 2026-11-04 (A-05)، بعد عرض ثلاثة خيارات وتبعاتها صريحةً.

### التبعات المقبولة صراحةً
1. **يُعدّل §3 من وثيقة المتطلبات** الذي كان يتيح الكود بديلًا لمن لا يملك رقمًا. الوثيقة تبقى محفوظة كما هي؛ التعديل يسكن هنا وفي `DECISIONS.md` (C-28) حتى تُصدر نسخة 1.1 موقعة.
2. **الطالب الذي لا يملك أي رقم (لا هاتفه ولا رقم ولي أمره) لن يستطيع الدخول.** يبقى له ملف أكاديمي عند المدرس (حضور، درجات، ملاحظات) يُدار من المدرس، لكنه لا يسجل دخوله. موثق في `KNOWN_LIMITATIONS.md` L-23.
3. `student_code` يبقى موجودًا كـ**معرّف عرض وبحث** داخل مساحة المدرس (فريد عالميًا)، **لا كوسيلة دخول**، ولا يُستخدم في أي مسار مصادقة.

### كيف تعمل الهوية الآن (فوق Supabase Auth)
- المدرس يُدخل رقم الطالب بصيغة `+20…` (تحقق شكلي)، فيُنشأ المستخدم من الخادم:
  `admin.createUser({ phone, password, phone_confirm: true })` ⇒ **لا تُرسل أي رسالة SMS**.
- الطالب يدخل بـ`signInWithPassword` عبر الهاتف (عبر `auth-login` لضبط حدّ المعدل والتدقيق).
- صحة الصيغة **لا تثبت ملكية الرقم** — لا يوجد إثبات ملكية بلا SMS، وهذا خطر معلن (L-25) وليس خطأً في التنفيذ.
- رقم ولي الأمر يبقى **للتواصل فقط** ولا يُستخدم كهوية دخول تلقائيًا (كما في §3 من المتطلبات).

### الخيارات التي رُفضت (محفوظة للتاريخ)
| الخيار | لماذا رُفض |
|---|---|
| مصادقة مخصصة للطلاب (كود + كلمة مرور بإيدينا) | شغل إضافي ومسؤولية أمنية أكبر مقابل ميزة لم يطلبها العميل بعد حسم C-28 |
| معرّف داخلي بصيغة بريد | يخالف §3 نصًا، ولا داعي له بعد إلغاء الكود |

### ما يعنيه ذلك للمرحلتين ٠٢ و٠٤
- المرحلة ٠٢: مسار واحد للدخول (هاتف) + استعادة + حدّ معدل + تدقيق. **لا ازدواج مسارات**.
- المرحلة ٠٤: عند إضافة طالب، حقل الهاتف **إلزامي**؛ وغيابه يمنع إنشاء حساب دخول (ويُسمح بالملف بلا حساب بحالة «بلا وصول» يجوز للمدرس إضافتها لاحقًا).

## ٣) مسارات الدخول

### أ) دخول عادي (عبر Edge Function `auth-login`)
```text
المتصفح → POST /functions/v1/auth-login { identifier, password, kind? }
  ├─ المدخل: رقم هاتف بصيغة E.164 فقط (لا كود — C-28)
  ├─ حدّ معدل: 5 محاولات / 15 دقيقة لكل (معرّف + IP-hash)، و20 / IP / ساعة
  ├─ Supabase Auth: token?grant_type=password (هاتف)
  ├─ عند النجاح: كتابة audit + إرجاع الجلسة (access/refresh) للعميل
  └─ عند الفشل: رسالة موحّدة «بيانات الدخول غير صحيحة» (لا نفرّق بين «لا يوجد حساب» و«كلمة خاطئة»)
```
**لماذا عبر دالة وليس من المتصفح مباشرة؟** لتوحيد حدّ المعدل والتدقيق، ومنع تعداد الحسابات. التكلفة: مسار إضافي يجب أن يكون idempotent وسريعًا.

### ب) دعوة مدرس
```text
السوبر أدمن → ينشئ دعوة (نوع teacher_invite)
  → رمز عشوائي 32 بايت، يُحفظ **بصمته** sha256 فقط، صلاحية ٧٢ ساعة، استخدام مرة واحدة
  → الرابط يُسلَّم يدويًا (نسخ/واتساب يدوي خارج المنصة) — لا بريد تلقائي
المدرس يفتح /pages/auth/accept-invitation؟token=… → يضبط كلمة المرور → يُنشأ الحساب ويُفعّل
```

### ج) دعوة ربط طالب (C-08)
```text
المدرس ينشئ ملف طالب محلي (status=pending_link) → يولّد student_link token
  ├─ طالب جديد: يفتح الرابط → ينشئ هوية (هاتف/كود) + كلمة مرور → يُربط
  ├─ طالب لديه حساب: يسجّل دخوله **أولًا** ثم يقبل الربط
  └─ لا ربط تلقائي بتشابه الهاتف أو الاسم
```

### د) استعادة كلمة المرور (C-09)
```text
المدرس يتحقق من هوية الطالب خارج النظام → يفتح «استعادة» في ملفه
  → Edge Function auth-recovery: ينشئ recovery_token (بصمة، ٣٠ دقيقة، مرة واحدة)
  → audit: من أصدر، لمن، السبب (إلزامي)
الطالب يفتح /reset-password?token=… → يضع كلمة مرور جديدة
  → الدالة تحدّث كلمة المرور عبر admin API (لا تُخزَّن ولا تُسجَّل)
  → **إبطال الجلسات** (§٥) + إشعار داخلي لكل مدرس مرتبط بالحساب
```

**ما لا يحدث:** المدرس لا يرى الكلمة القديمة أو الجديدة، ولا يستطيع الدخول بحساب الطالب.

## ٤) حدّ المعدل (Rate Limiting)

| المسار | الحد المقترح | التنفيذ |
|---|---|---|
| تسجيل الدخول | ٥ محاولات / ١٥ دقيقة لكل معرّف، ٢٠ / IP / ساعة | جدول `app.login_attempts` + دالة ذرية |
| إصدار استعادة | ٣ / ساعة لكل مدرس، ٥ / يوم لكل طالب | نفس الآلية + تدقيق |
| قبول دعوة | ١٠ محاولات / ساعة لكل IP | عدّاد بسيط |
| أي مسار حسّاس | حد أعلى عام | طبقة وسيطة في `_shared/rate-limit.js` |

**تخزين العدّاد:** جدول في PostgreSQL (لا Redis — C-20/الدستور)، مع فهرسة على (المفتاح، النافذة) وتنظيف دوري.

## ٥) إبطال الجلسات (سياسة تحتاج اعتمادًا)

| الحالة | ما يحدث فورًا | ما يتبقى |
|---|---|---|
| إيقاف حساب (`suspended`) | كل RLS/RPC تتحقق من `profiles.status` ⇒ **الطلبات الجديدة تُرفض** | التوكن الحالي يبقى صالحًا حتى انتهاء `exp` — لذلك **exp = ١ ساعة**، والرفض يحدث في كل طلب رغم ذلك |
| تغيير كلمة المرور | تحديث `profiles.sessions_valid_after = now()` + `admin.signOut(user_id, 'global')` | جلسة لم تُحدَّث قد تنجح حتى انتهاء التوكن إن لم تُفحص `sessions_valid_after` |
| حذف/أرشفة | رفض فوري في كل طلب | نفس أعلاه |

**قاعدة ملزمة:** سياسة RLS لا تكتفي بوجود JWT؛ تتحقق من `profiles.status='active'` **و** `auth.jwt()->>'iat' >= sessions_valid_after`. هذا ما يجعل الإيقاف فوريًا عمليًا.

## ٦) المصادقة الثنائية للسوبر أدمن (R-09)

- TOTP عبر Supabase MFA (عند توفرها في المشروع) أو طبقة Edge Function مستقلة.
- **رموز استعادة** تُسلَّم للعميل خارج المنصة (ورق/مدير كلمات مرور) — ليست في المستودع.
- عند فقدان الجهاز: مسار استعادة إداري موثق يحتاج وصولًا لقاعدة البيانات (ليس من الواجهة).
- **لم يُتحقق** من دعم MFA في الخطة المتاحة ⇒ بند تحقق في المرحلة ٠٣.

## ٧) الخطر المتبقي — **قبله العميل صراحةً (C-32)**

> **الحساب العالمي يعني أن استعادة كلمة مرور واحدة قد تفتح مساحات عدة مدرسين.**

يمكن أن يحدث هذا في سيناريوهين:
1. مدرس استعادة «سيئ النية أو مُخدَع» يصدر رابطًا لشخص ليس الطالب.
2. الطالب نفسه يستلم الرابط ويُشاركه عن غير قصد.

**ضوابط تقليل الخطر:**
- إشعار داخلي لكل مدرس مرتبط فور الاستعادة أو تغيير كلمة المرور.
- تسجيل كامل (من، لمن، متى، لماذا) لا يُحذف.
- صلاحية الرابط ٣٠ دقيقة واستخدام مرة واحدة.
- **اقتراح إضافي (يحتاج اعتمادًا):** «مدرس استعادة أساسي» يختاره الطالب من حسابه، ولا تُقبل الاستعادة من غيره إلا بعد ٢٤ ساعة إشعار.
- **اقتراح ثانٍ:** عامل تحقق إضافي يملكه الطالب (رقم ولي أمر للتواصل، أو سؤال سري) لا يمنح دخولًا بذاته.

**لا يجوز تسويق النظام بأنه يمنع هذا السيناريو بالكامل.** القبول النهائي لهذا الخطر قرار العميل.

## ٨) ما يجب التحقق منه عمليًا في المرحلة ٠٢ (لا تُفترض — تُختبر)

| # | الفرضية | كيف تُختبر (المرحلة ٠٢، أول يوم) | إن فشلت |
|---|---|---|---|
| 1 | إنشاء مستخدم بهاتف مع `phone_confirm` بلا إرسال SMS | استدعاء Admin API ومراقبة عدم وصول أي رسالة/خطأ | نعود لمسار بديل ونعيد فتح القرار |
| 2 | `signInWithPassword` بالهاتف يعمل بلا تأكيد OTP | محاولة دخول فعلية بحساب اختباري | نفس البديل |
| 3 | `admin.signOut(user_id,'global')` يُبطل الجلسات | إبطال ثم طلب بجلسة قديمة | نعتمد على `sessions_valid_after` في RLS |
| 4 | MFA متاحة في الخطة الأرخص | تشغيل TOTP لسوبر أدمن | نؤجل R-09 ونوثّق الخطر |
| 5 | حدّ المعدل الذاتي يعمل مع الاستدعاء من المتصفح | ٦ محاولات خاطئة متتالية | ننقل الحدّ بالكامل للدالة |

## ٩) علاقة المصادقة بنموذج البيانات

- `auth.users` هوية عالمية واحدة (C-03).
- `app.profiles` يحمل الدور والحالة و`student_code` و`session_valid_after`.
- `app.teacher_memberships` تصل المستخدم بمساحات المدرسين.
- لا يوجد في أي جدول من جداولنا حقل كلمة مرور (C-25).
