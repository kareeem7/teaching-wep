# السياق المشترك لمشروع منصة المدرّسين والطلاب والامتحانات

> هذا الملف مرجع مختصر لجميع مراحل التنفيذ والفحص. أرفقه مرة في بداية المشروع في المحادثة، أو احتفظ به داخل المستودع في المسار `phase-prompts/00-project-context.md`. المرجع التفصيلي هو `01-requirements-ar.md` عند توفره، والقرارات المعتمدة في `docs/DECISIONS.md`.

## طبيعة المشروع

منصة تساعد المدرّس على إدارة طلابه ومجموعاته وحضورهم ودرجاتهم ودروسهم وامتحاناتهم. ليست سوق كورسات عامة، وليست نظام إدارة سنتر متعدد الإدارات.

## القرارات الأساسية

- الأدوار: سوبر أدمن، مدرس، مساعد مدرس، طالب.
- كل مدرس له مساحة مستقلة. السنتر أو البلد مجرد مكان داخل مساحة المدرس؛ تشابه الأسماء لا يشارك البيانات.
- الطالب له حساب عالمي واحد، وملف أكاديمي مستقل لدى كل مدرس. لا يرى بيانات طالب آخر أو مدرس غير مرتبط به.
- السوبر أدمن يدير الحسابات ويدعو المدرسين ويتابع ويرسل تعليمات؛ وصوله للبيانات الأكاديمية للقراءة فقط، بلا تعديل حضور أو درجات أو إجابات، وبلا انتحال هوية مدرس.
- المدرس يمنح المساعدين صلاحيات أفعال ومجموعات محددة. لا يتجاوز المساعد نطاقه، حتى عبر طلب API مباشر.
- دخول الطالب: هاتف وكلمة مرور، أو كود طالب فريد وكلمة مرور عند عدم وجود رقم مستقل. رقم ولي الأمر للتواصل وليس حسابًا مشتركًا للأبناء.
- المدرسون بدعوة من الإدارة فقط. استعادة الطالب بمساعدة المدرس وفق ضوابط المرحلة صفر؛ لا SMS مدفوع ولا بريد إلزامي.
- الطلاب: اسم، صف، مادة، مكان/سنتر، مجموعة وميعاد، هاتف، وولي أمر اختياري. أمثلة: «مليج الساعة ٧»، «شبين الساعة ٦».
- الحضور: حاضر/غائب/متأخر/غياب بعذر، وسياسة حساب معتمدة، وسجل تعديل. عدم الرصد ليس غيابًا تلقائيًا.
- الدروس: شرح وصور ومعادلات، وفيديو يوتيوب مضمن داخل المنصة. لا رفع فيديو ذاتي في الإصدار الأول.
- الامتحانات: اختيار من متعدد بإجابة صحيحة واحدة، وصح/خطأ، مع صور ومعادلات. لا مقالي في الإصدار الأول.
- بنك ١٠٠ سؤال وسحب ١٠ لكل طالب مثال قبول أساسي. السحب مستقل وعشوائي، لا يتكرر السؤال داخل المحاولة، ويخلط ترتيب الأسئلة والاختيارات. مسموح بتقاطع أسئلة بين الطلاب.
- نسخة المحاولة ثابتة على الخادم. الانقطاع أو تحديث الصفحة لا يعيد الوقت ولا ينشئ محاولة جديدة. الحفظ والتسليم والتصحيح على الخادم.
- المدرس يحدد التوقيت والمدة وعدد المحاولات، وأعلى/آخر نتيجة، وإظهار الدرجة والمراجعة كلًا على حدة.
- الحماية: ملء الشاشة عند الدعم، وتسجيل مغادرة الصفحة عند التفعيل. الأحداث مؤشرات مراجعة، وليست إثبات غش. لا كاميرا ولا إنهاء تلقائي لمجرد فقدان التركيز.
- التنبيهات داخل المنصة فقط. الهدف ١٠٠–١٠٠٠ طالب متزامن كهدف اختبار على موارد محددة، وليس ضمانًا قبل القياس.
- الواجهة عربية RTL، بسيطة، عملية، ومتجاوبة. أقل تكلفة مع حماية البيانات والنسخ الاحتياطي.

## خارج الإصدار الأول

المصاريف والدفع، اشتراكات المنصة، المقالي، بوابة ولي الأمر، واتساب/SMS، البث المباشر، رفع الفيديو، المراقبة بالكاميرا، مدير سنتر مستقل، والتطبيق الأصلي. لا تضف هذه الميزات دون طلب مستقل.

## الحزمة التقنية المعتمدة

اعتمد العميل: واجهة HTML5 + CSS3 + Bootstrap 5 RTL + JavaScript ES Modules، وخلفية Supabase. استخدم Supabase PostgreSQL وAuth وStorage وEdge Functions وRLS. لا Laravel ولا Inertia ولا React ولا Tailwind. لا تضف إطار واجهة أو خدمة مدفوعة دون موافقة صريحة.

### قواعد Supabase الملزمة

- المتصفح يستخدم Supabase URL وpublishable/anon key فقط. لا service_role key ولا أسرار في `public/` أو Git.
- كل جدول عليه بيانات مستخدم يجب أن يكون RLS مفعلًا ومختبرًا، والسياسات لا تعتمد على قيم يرسلها العميل مثل teacher_id كدليل ملكية.
- العمليات الحساسة: الدعوات، الاستعادة، بدء المحاولة، الحفظ، التسليم، التصحيح، إغلاق الوقت، التصدير، والتنبيهات الجماعية تكون في Edge Functions أو SQL/RPC ذري، وليس في المتصفح.
- مفاتيح الإجابة والنسخ المرجعية لا تصل للطالب قبل السماح. الوقت والتصحيح والسحب العشوائي مرجعها الخادم.
- التخزين خاص، والوصول عبر signed URLs أو سياسات Storage مضبوطة.
- المهام الخلفية عبر Edge Functions وpg_cron/آلية معتمدة عند الحاجة، مع idempotency ومراقبة، دون افتراض Redis أو خادم تطبيق تقليدي.
- اختبارات التكامل على Supabase PostgreSQL منعزل، مع RLS. لا تمس بيانات إنتاج.

## قواعد تنفيذ وفحص ملزمة

قواعد الكود وقاعدة البيانات والاختبارات البرمجية تنطبق على مراحل البرمجة. المرحلة صفر وثائق وتصميم فقط، ولا تنشئ فيها تطبيقًا أو قاعدة بيانات.

1. افحص الملفات والقرارات وحالة المشروع قبل التغيير. حافظ على عمل المستخدم ولا تهدم مشروعًا قائمًا.
2. مرحلة واحدة فقط في كل رسالة تنفيذ. لا تبدأ التالية قبل نجاح الفحص واعتماد العميل الصريح.
3. الصلاحيات على الخادم لكل قراءة وكتابة وتصدير. لا تمنح الإدارة تجاوزًا يسمح بالكتابة الأكاديمية.
4. اختبر عزل مدرسين، ومساعدًا مقيدًا، وطالبًا لدى مدرسين. الطالب في عدة مجموعات لا يُعد مرتين في الإجمالي الفريد.
5. كلمات المرور بتجزئة آمنة، والرموز العشوائية أحادية الاستخدام ومحدودة الصلاحية ومحفوظة كبصمات. لا أسرار أو بيانات طلاب حقيقية في المستودع أو اللقطات.
6. قيود قاعدة البيانات والمعاملات والفرادة ضرورية. اختبارات التكامل على Supabase PostgreSQL منعزل مع RLS، وليس على بيانات إنتاج.
7. Supabase migrations آمنة. لا reset أو حذف بيانات على بيئة حقيقية. النسخ الاحتياطي قبل التغييرات الخطرة.
8. المهام الحساسة آمنة من التكرار؛ لا ازدواج حضور أو محاولة أو نتيجة أو تنبيه منطقي.
9. أزمنة UTC على الخادم وعرض بالمنطقة المعتمدة. ساعة الطالب ليست مرجعًا للوقت.
10. لا تخلط نجاحًا حقيقيًا بمحاكاة. سجل أوامر الفحص والبيئة والنتيجة والأعداد والأدلة. اختبار لم يعمل = لم يُتحقق منه، وليس نجاحًا.
11. شغّل اختبارات المراحل السابقة المكتملة مع كل مرحلة. الوظائف المستقبلية «غير منطبقة بعد»، ولا تُحسب نجاحًا.
12. لا انتقال مع عيب حرج/عالٍ، أو خرق صلاحيات، أو فقدان بيانات. عيوب أقل تحتاج قرار قبول موثقًا، لا تجاهلًا.
13. لا شراء خدمات أو نشر إنتاج أو استخدام بيانات حقيقية دون إذن صريح. جهز البديل المحلي عند نقص خدمة خارجية.
14. لا تستخدم مشاريع Supabase الأخرى الموجودة في الحساب، مثل مشاريع clinic، إلا بطلب صريح. أنشئ/اربط مشروع المنصة فقط بعد اعتماد المرحلة صفر وإذن العميل.
15. في بيئة المعاينة السحابية: اربط الخادم بـ 0.0.0.0، واسمح بمضيف المعاينة، واستخدم مسارات نسبية في المتصفح. لا تجعل المتصفح يطلب localhost للوصول لخدمة أخرى. استخدم أدوات العمليات الطويلة المتاحة بدل أوامر bash التي تنتظر للأبد.
16. حدّث `docs/PROJECT_STATE.md` و`docs/REQUIREMENTS_TRACEABILITY.md` و`docs/KNOWN_LIMITATIONS.md`. احفظ تقرير البناء في `docs/PHASE_REPORTS/PHASE_XX_BUILD.md` وتقرير الفحص في `PHASE_XX_CHECK.md`.
17. اعتماد العميل يسجل في `docs/APPROVALS.md` بناء على رسالته الصريحة. لا يكتب الوكيل موافقة نيابة عنه.
18. أنشئ الملفات والفولدرات بالأسماء والمسارات المحددة في `05-project-structure-ar.md` وقائمة كل مرحلة، ووثّق أي تعديل في `docs/DECISIONS.md`. لا أسماء عشوائية ولا تنظيم موازٍ ولا ملفات فارغة.

## سياسة GitHub والرفع التلقائي

- أول رفع على الريبو يبدأ مع كود المرحلة ٠١ بعد اعتماد المرحلة صفر؛ لا ترفع وثائق التخطيط الحالية الآن لمجرد تجهيز الريبو.
- استخدم فرعًا لكل مرحلة مثل `phase/08-attempt-engine`، ولا ترفع مباشرة على الفرع الأساسي.
- بعد دفعات التنفيذ الناجحة محليًا، اعمل commits واضحة وارفع فرع المرحلة إذا كانت بيئة Git مصرحًا لها بالرفع. لا ترفع أسرارًا أو `.env` أو بيانات طلاب حقيقية.
- الفحص يراجع نفس الفرع والـ commit. لا دمج قبل `PASS` واعتماد العميل الصريح.
- إذا توفر `gh` أو GitHub API مصرح به، افتح/حدث Pull Request. إذا كان Git push فقط متاحًا، ارفع الفرع وسجل رابط مقارنة جاهزًا و`PR_BLOCKED` إن لزم.
- عند فشل الرفع سجل `PUSH_BLOCKED` ولا تدّعي النجاح. لا force push ولا reset قسري ولا حذف لتغييرات المستخدم.
- التفاصيل في `04-github-workflow-ar.md`.
