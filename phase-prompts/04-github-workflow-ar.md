# سياسة GitHub والتنظيم التلقائي للريبو

## القرار المعتمد من العميل

- الوصول: بيئة Git مصرح لها بالرفع، وليس موصل GitHub مباشر داخل المحادثة.
- سياسة الرفع: **فرع لكل مرحلة + Pull Request**.
- أول رفع: **يبدأ مع كود المرحلة ٠١** بعد اعتماد المرحلة صفر، وليس برفع وثائق التخطيط الحالية الآن.

## القاعدة الأساسية

لا رفع مباشر على `main`. كل مرحلة تعمل على فرع مستقل، وتُفحص، ثم تُدمج عبر PR بعد اعتماد العميل.

## دورة كل مرحلة

### 1. قبل البدء

- افحص `git status` وحافظ على أي تغييرات غير ملتزم بها.
- اجلب آخر نسخة من الفرع الأساسي: `git fetch origin`.
- أنشئ فرع المرحلة من الفرع الأساسي المعتمد.
- لا تستخدم `reset --hard` أو `clean -fd` أو force push.

### 2. أثناء التنفيذ

- قسم المرحلة إلى دفعات صغيرة.
- بعد كل دفعة ناجحة محليًا، اعمل commit واضحًا.
- ارفع الفرع إلى `origin` إذا كانت بيئة Git مصرحًا لها بالرفع.
- صيغة الرسالة: `feat(phase-08): add server-side attempt saving` أو `fix(phase-08): prevent duplicate submission`.
- لا ترفع أسرارًا، ملفات `.env`، مفاتيح، كلمات مرور، أو بيانات طلاب حقيقية.

### 3. بعد التنفيذ

- شغل فحوص المرحلة والفحوص التراكمية المنطبقة.
- احفظ التقارير في `docs/PHASE_REPORTS/`.
- اعمل commit للتقارير: `docs(phase-08): add build and test evidence`.
- ارفع الفرع.

### 4. الفحص

- الفاحص يراجع نفس الفرع/نفس الـ commit.
- يحفظ تقرير الفحص وأي اختبارات تحقق منفصلة محليًا، ولا يعدل كود المنتج ولا يدمج ولا يعتمد نفسه.
- بعد انتهاء الفحص، المنفذ يرفع تقرير الفحص على فرع المرحلة: `test(phase-08): add independent verification evidence`.

### 5. Pull Request

- يمكن فتح PR مسودة من فرع المرحلة إلى الفرع الأساسي بعد رفع فرع المرحلة.
- بعد `PASS` ورفع تقرير الفحص، يصبح PR جاهزًا للمراجعة.
- عنوان PR: `Phase 08 — Server attempt engine`.
- الوصف يشمل: نطاق المرحلة، ما لم ينفذ، روابط التقارير، نتائج الفحص، القيود، وما يحتاج اعتماد العميل.
- إذا كانت نتيجة الفحص `FAIL` أو `BLOCKED`، يبقى PR مسودة أو غير جاهز للدمج.
- إذا كانت `PASS`، يطلب اعتماد العميل الصريح.

### 6. الدمج

- لا دمج قبل اعتماد العميل.
- بعد الاعتماد، يدمج PR وفق سياسة الريبو.
- يُحدّث `docs/APPROVALS.md` و`docs/PROJECT_STATE.md`.
- لا تبدأ المرحلة التالية إلا بعد الدمج أو توثيق سبب التأجيل.

## فتح PR تلقائيًا

- إذا كانت البيئة فيها `gh` مسجل الدخول أو GitHub API مصرح به، يفتح PR تلقائيًا.
- إذا كان Git push فقط متاحًا، يرفع الفرع ويولد رابط مقارنة جاهزًا لفتح PR، مثل:
  `https://github.com/OWNER/REPO/compare/main...phase/08-attempt-engine?expand=1`
- لا تطلب رمز وصول (token) في المحادثة. الصلاحيات تكون عبر بيئة Git الآمنة.

## هيكل الريبو

الأسماء الملزمة للملفات والفولدرات موجودة في `05-project-structure-ar.md` (شجرة عامة + قائمة ملفات كل مرحلة). لا ينشئ الوكيل تنظيمًا موازيًا ولا أسماء من عنده؛ أي تعديل يتوثق في `docs/DECISIONS.md` ويحدّث ملف الشجرة في نفس الـ commit.

## حماية الفرع الأساسي

يوصى بتفعيل:

- منع force push.
- منع الحذف.
- طلب PR قبل الدمج.
- طلب نجاح CI.
- طلب مراجعة/اعتماد حسب سياسة المشروع.

## عند غياب الوصول أو فشل الرفع

- لا تدّعي أن الكود اترفع.
- احفظ التغييرات محليًا في commits إن أمكن.
- سجل الحالة `PUSH_BLOCKED` أو `PR_BLOCKED` مع السبب.
- اطلب ضبط صلاحية Git أو remote، ولا تطلب أسرارًا داخل الشات.
